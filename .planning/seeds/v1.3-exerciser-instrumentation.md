# v1.3 seed — Exerciser instrumentation needs DOM-id or equivalent target hook

## Problem

Phase 19 Plans 19-02/03/04 shipped three frontend instrumentation modules:

- `frontend/src/lib/exer01/observe.svelte.ts` — probes the nested `AppShell`
  collision by reading Svelte context on `Symbol.for('scn-sidebar')` and
  comparing it against a DEV-gated `window.__mrnExer01OuterSidebar` hook.
- `frontend/src/lib/exer02/invariants.svelte.ts` — wires 4 DOM watchers on
  the focused input (focus, cursor, typed-value integrity, IME composition)
  and a client-initiated tick loop that calls
  `sendAction('gallery-demo/exer-02/tick')` at the selected cadence.
- `frontend/src/lib/exer03/perf.svelte.ts` — captures TTFP, scroll FPS,
  memory, and patch-latency p95 and round-trips them to the backend via
  `gallery-demo/exer-03/report-perf`.

The EXER-02 `autoArm()` and EXER-03 perf module locate their targets by
`document.getElementById('exer-02-focused-input')` and
`document.querySelector('#exer-03-perf-ttfp')` respectively. Phase 19-05
Chrome / Playwright UAT confirmed the frontend renderer does **not**
propagate SDUI component ids (as set by `Text::new(...).id("exer-02-…")`
on the backend) to DOM `id` attributes. The component id is used by the
surface store for indexing and patch targeting, but the rendered HTML
element receives no corresponding `id` attribute by default. As a result
the two instrumentation modules' MutationObserver callbacks never arm in
the browser, even after being imported from `init.ts`.

Server-side verification remains clean: the Plan 19-05 WebSocket probe
confirmed 19 patches in 10 s at 500 ms cadence with **0 Pitfall 2
violations**, 4 perf badges correctly switch between `WITHIN TARGET` /
`OVER TARGET`, and the 10 000-row fetch-rows source returns the first
and last 50-row pages correctly. All 9+9+10 unit tests for the three
instrumentation modules pass in vitest. The gap is strictly the browser-
runtime bridge between SDUI component ids and DOM id attributes.

## Proposed scope

Three implementation options — in order of preference:

### Option A — Emit component ids as `data-sdui-id` (RECOMMENDED)

- **Why:** `id` is globally unique per HTML spec; emitting arbitrary backend
  strings as `id` can conflict with shadcn-svelte's internal id generation
  (Field.Field assigns its own ids via bits-ui) and with CSS selectors
  that target `#…`. `data-*` attributes are free of those constraints
  and match the conventional accessibility-linting posture.
- **Scope:**
  - Modify `frontend/src/lib/components/core/NodeRenderer.svelte` (or the
    equivalent component-boundary wrapper) to set
    `data-sdui-id={componentId}` on the rendered element root for every
    SDUI component. Single-line HTML-attribute bridge.
  - Rewrite the three exerciser modules to use
    `document.querySelector('[data-sdui-id="exer-02-focused-input"]')`
    everywhere they currently use `getElementById`.
- **Risk:** Low — purely additive, no breaking change to protocol or store
  shape. shadcn-svelte primitives already accept arbitrary HTML attributes
  via Svelte's `{...restProps}` spread.
- **Effort:** ~2 hours (1 hour wiring NodeRenderer + 1 hour rewriting
  three probe modules + vitest fixture updates).

### Option B — Emit component ids as `id` attribute (explicit opt-in)

- Same as Option A but uses the native `id` attribute. Requires careful
  handling of collisions (especially Field.Field and Popover anchors).
- **Risk:** Medium — collisions with shadcn-svelte bits-ui `id` generation
  may break focus management.
- **Effort:** ~4 hours (including collision audit and shim for conflicts).

### Option C — Svelte-mount hook on SDUI components (most invasive)

- Each SDUI component exports an `onMount` callback that instrumentation
  modules can subscribe to by component type or id.
- **Risk:** High — introduces a new framework concept, expands registry
  contract, couples framework crate to gallery-demo use cases.
- **Effort:** ~1-2 days (new registry API, migration of 25+ components,
  new test surface).

## Acceptance

v1.3 phase closes this seed when:

- [ ] A way to locate SDUI component DOM roots by backend-assigned id is
      in place (preferred: Option A `data-sdui-id`).
- [ ] `frontend/src/lib/exer02/invariants.svelte.ts::autoArm()` successfully
      mounts its 4 watchers on the focused input when the EXER-02 screen is
      visible in the browser — verified by a Playwright test that types
      into the input, clicks Start patching, waits 60 s × 500 ms cadence,
      and asserts:
      - `patch log` contains ≥ 120 rows
      - all 4 invariant badges have flipped from `PENDING` to `PASS`
      - the input retains focus (activeElement === the focused input)
      - the typed value is preserved byte-for-byte
- [ ] `frontend/src/lib/exer03/perf.svelte.ts` successfully mounts and
      reports perf signals — verified by a Playwright test that visits
      EXER-03, waits 30 s, asserts all 4 perf cells show numeric values
      (not `—` em-dash), and confirms at least one
      `gallery-demo/exer-03/report-perf` action was sent on the wire.
- [ ] The v1.3 seed file is updated to reference the closing plan.
