<objective>
Close the five handler-layer / sub-surface / demo-body gaps surfaced by Phase 17 UAT (G-01, G-03, G-04, G-06, G-07).

Four of these gaps share the backend `gallery-demo/src/handlers/*.rs` layer plus one tightly-scoped frontend close-semantics touch on `ModalSurface.svelte`. G-03 touches a single line in the DataTable builder demo fn (colocated in `marionette/src/builders/data_table.rs` per D-B3). Plan 17-06 (sibling, Wave 1) owns the remaining demo-body fixes (G-02, G-05).

**Root causes locked at planning time (verified against source files on 2026-04-22):**

1. **G-01 Modal lockup** — `handle_modal_open` currently renders a `Modal::new(...).build_with_children()` Component (serialized as `type: "modal"`) into the `modal` sub-surface (see `backend/crates/gallery-demo/src/handlers/modal.rs:23`). The frontend registry maps `"modal"` → `ModalSurface.svelte` (`frontend/src/lib/registry/defaults.ts:57`), and `ModalSurface` itself calls `getSurfaceTree('modal')`. `NodeRenderer` tries to render the modal tree's root, resolves `type: "modal"` → a second `ModalSurface`, which reads `getSurfaceTree('modal')` again → infinite reactive recursion → tab lockup.

2. **G-04 ConfirmDialog doesn't dismiss** — `ModalSurface.svelte:8` computes `isOpen = $derived(tree !== undefined)`. Once any Render lands on the `modal` sub-surface, `setSurfaceTree` creates the tree and `isOpen` stays `true` forever. The existing `handle_confirm_accept/reject` handlers ARE rendering an empty Container (id="modal-empty") to clear the modal (`handlers/confirm.rs:59-98`), but `tree` still exists (it's the Container), so `isOpen` stays `true`. Fix: teach `isOpen` to return `false` when the tree's root is an empty Container — the canonical "closed" sentinel already emitted by the backend.

3. **G-06 Home footer oversized** — `navigate.rs:51,54` uses `Heading::new(...)` for the footer version + connection-status lines. Heading renders as `<h2 class="text-xl font-semibold">`, overriding the footer wrapper's `text-xs text-muted-foreground`. Change to `Text::new(...)`.

4. **G-07 Modal sub-surface unseeded** — `navigate.rs` currently seeds `toasts` with an empty Container (good — matches CRM pattern at `crm-demo/src/main.rs:293-309`), but does NOT seed `modal`. An unseeded sub-surface's `SurfaceMount` renders a LoadingSkeleton placeholder (visible as grey bars below the footer). Add a 4th Render for `modal` with an empty Container root, mirroring the toasts seed.

5. **G-03 DataTable empty — CORRECTED DIAGNOSIS (pass-2 planning).**

   The original plan (pass 1) claimed "fetch_rows emits per-row Set ops (object-map) but DataTable frontend expects an ARRAY." That was **wrong**. Static re-analysis on 2026-04-22:

   - `frontend/src/lib/components/table/DataTable.svelte:113-119` reads rows via:
     ```svelte
     const rawData = $derived(
         bind
             ? ((getData(surface, bind) as Record<string, Record<string, unknown>>) ?? {})
             : {},
     );
     const rowEntries = $derived(Object.entries(rawData));
     const rows = $derived(rowEntries.map(([, v]) => v));
     ```
     The frontend EXPECTS an object-map keyed by id (iterated via `Object.entries`). Per-row Sets keyed by id produce exactly that shape. ✅ Shape is correct.

   - CRM's `crm-demo/src/handlers/fetch_rows.rs:136-149` is the PROVEN pattern: emits ONE `PatchOperation::Set` per row at path `{source_path}/{row_id}`, with `source_path` returned by the per-source fetcher (e.g. `fetch_contacts` returns `("/contacts", rows)` at lines 168-192). Gallery's `handle_demo_fetch_rows` already does the same shape: one `Set` per row at `/demo/data-table/rows/{row_id}`.

   - `seed_for_key("data-table")` (in `gallery-demo/src/handlers/show.rs:66`) seeds an ARRAY at `/demo/data-table/rows`. That array seed ALSO needs to become an object-map keyed by id to match the frontend's `Object.entries` iteration; alternatively it can simply be removed (fetch_rows will overwrite on DataTable mount). We choose to KEEP a non-empty seed so the DataTable shows rows pre-fetch (important for snappy first paint) AND switch the seed shape to an object-map.

   - **Actual root cause:** `backend/crates/marionette/src/builders/data_table.rs:240-249`'s `gallery_demo()` body sets `.source("demo-rows")` and `.row_id_key("id")` but does NOT call `.bind(...)`. Per `DataTable.svelte:113`, `bind ? getData(...) : {}` — no bind means `rawData` is always `{}` and the table always has 0 rows, regardless of what `fetch_rows` emits or what `seed_for_key` seeds.

   - **Fix:**
     (a) Add `.bind("/demo/data-table/rows")` to the DataTable builder chain in the demo fn.
     (b) Rewrite `seed_for_key("data-table")` in `gallery-demo/src/handlers/show.rs` to emit an object-map keyed by id, matching CRM's proven pattern (`{"1": {id:1, ...}, "2": {...}, ...}`).
     (c) Keep `handle_demo_fetch_rows` EXACTLY AS-IS — per-row Set ops at `/demo/data-table/rows/{row_id}` is the correct CRM-aligned pattern.
