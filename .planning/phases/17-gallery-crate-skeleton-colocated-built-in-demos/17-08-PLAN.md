<objective>
Close gap G-08 (stranded `Modal` builder). Plan 17-05 relocated `ModalSurface` to a layout-root singleton mount and unregistered the `'modal': ModalSurface` component-type dispatch in `frontend/src/lib/registry/defaults.ts`. That change correctly implements the user's architectural decision (2026-04-22): *popups work independent of any other component; composition over dedicated primitives*. But it left behind a producer — the `Modal` struct in `backend/crates/marionette/src/builders/modal.rs` still emits nodes of `type = "modal"` that the frontend registry no longer dispatches. Any call to `Modal::new(...)` today produces a dead node.

This plan deletes the stranded `Modal` primitive, cleans up its publish sites, updates the component-type smoke-test expectation, and documents the compositional popup pattern in `GALLERY-DEMOS.md` so future handler authors default to "emit any SDUI tree into the `modal` sub-surface" instead of reaching for a non-existent `Modal::new` wrapper. `ConfirmDialog` (the structured accept-cancel variant) stays — it remains useful as a purpose-built primitive. `Toast`, `Spinner`, `ErrorDisplay`, and all other dialog-adjacent components are untouched.

This is an **autonomous** plan — purely code-and-docs cleanup, no runtime verification beyond `cargo build` / `cargo test` / `cargo clippy`.
</objective>

<root_cause>
`#[derive(ComponentBuilder)] pub struct Modal { title, size } #[component(type = "modal")]` in `backend/crates/marionette/src/builders/modal.rs:7-13` produces SDUI nodes of type `"modal"`. Before Plan 17-05, the frontend registry entry `'modal': ModalSurface` in `frontend/src/lib/registry/defaults.ts` caused nodes of that type to render `ModalSurface.svelte` (which wraps in `<Dialog.Root>`). That dispatch caused the original G-01 infinite-recursion bug when `Modal::new(...)` was emitted INSIDE the `modal` sub-surface (ModalSurface reads `getSurfaceTree('modal')` hardcoded → it read its own tree → rendered itself again).

Plan 17-05 Task 6a/6b fixed the architecture by:
1. Mounting `<ModalSurface />` at the layout root (`+layout.svelte` — always-live, reads `modal` sub-surface, wraps in `Dialog.Root`)
2. Removing the `'modal': ModalSurface` SDUI-dispatch entry + the import from `defaults.ts`

After that change, the `Modal` builder's output (type `"modal"`) has no registered frontend renderer — it falls through to the unknown-type fallback. The producer must go.
</root_cause>

    ```markdown
    ## Popup composition

    The popup toolbox is **compositional, not primitive-based**. Phase 17 moved
    `ModalSurface.svelte` to a layout-root singleton mount — it is always live
    and wraps whatever SDUI tree you emit into the `modal` sub-surface in a
    shadcn `<Dialog.Root>` / `<Dialog.Content>` overlay.

    **To open a popup with arbitrary content**, render any SDUI tree (Container,
    Form, TextInput, Button, Heading, Text, …) to the `modal` sub-surface. The
    `<Dialog.Root>` open/close state is driven by ModalSurface's `isOpen`
    derivation: an empty `Container` root = closed; any non-empty tree = open.

    **To close a popup**, render an empty `Container` (id convention:
    `modal-empty`) into the `modal` sub-surface — ModalSurface observes the
    empty tree and dismisses the dialog. The frontend also dispatches a
    `close-modal` action when the user clicks the X button or backdrop; the
    gallery-demo's `handle_modal_close` handler implements that by rendering
    `modal-empty`.

    **Canonical "form in popup" recipe:**

    ```rust
    pub async fn open_contact_form(ctx: HandlerContext) -> ActionResult {
        use marionette::builders::{Button, Container, Form, Heading, TextInput};
        use marionette_protocol::{Component, ComponentAction};
        use marionette_protocol::messages::RenderMessage;

        let name = TextInput::new()
            .id("contact-name")
            .label("Name")
            .bind("/contact/name")
            .build();
        let email = TextInput::new()
            .id("contact-email")
            .label("Email")
            .bind("/contact/email")
            .build();
        let form = Form::new()
            .id("contact-form")
            .children(vec![name, email])
            .build();

        let cancel = Button::new("Cancel")
            .id("contact-cancel")
            .variant("outline")
            .action(ComponentAction::click("close-modal"))
            .build();
        let save = Button::new("Save")
            .id("contact-save")
            .variant("default")
            .action(ComponentAction::click("save-contact"))
            .build();
        let button_row = Container::new()
            .id("contact-button-row")
            .children(vec![cancel, save])
            .build();

        let heading = Heading::new("New contact")
            .id("contact-heading")
            .build();
        let dialog_nodes = Container::new()
            .id("contact-popup-root")
            .children(vec![heading, form, button_row])
            .build_with_children();

        let mut nodes: std::collections::HashMap<String, Component> =
            std::collections::HashMap::new();
        for (id, c) in dialog_nodes {
            nodes.insert(id, c);
        }

        Ok(vec![marionette_protocol::ProtocolMessage::Render(RenderMessage {
            id: ctx.action.id.clone(),
            surface: "modal".into(),
            root: "contact-popup-root".into(),
            nodes,
            data: serde_json::json!({}),
        })])
    }
    ```

    The Save handler does its side-effects (DB write, toast enqueue, etc.) and
    also renders `modal-empty` into the `modal` sub-surface to dismiss the
    dialog.

    **When to use `ConfirmDialog` instead:** if the popup is a simple two-
    choice accept/cancel prompt (title + message + two buttons), reach for the
    `ConfirmDialog` primitive — it encodes that shape directly. For anything
    more complex (form, multi-step, custom layout), compose from raw nodes as
    above.
    ```
