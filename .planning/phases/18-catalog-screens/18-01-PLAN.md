<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (browser) → backend WS | Action payloads (blur/click) cross this boundary; new Button fields are render-path only — no user input crosses into any new field here. |
| backend Rust → frontend Svelte | New Button fields serialize to JSON; Svelte reads them with `as string` / `as boolean`. Any malicious value from a compromised builder source would render as shadcn wrapper CSS class — bounded by shadcn's own variant enum. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-01-01 | Tampering | Button.svelte variant mapping | accept | `variant` is a string passed to shadcn's own variant prop; shadcn applies its own allowlist internally. An invalid variant string simply fails to match a CVA variant — no CSS injection possible (shadcn uses class-variance-authority, not string interpolation). Low risk; no PII. |
| T-18-01-02 | Information disclosure | `aria_label` string echo | accept | User-visible via screen readers only; no PII source feeds it in Phase 18 (every `aria_label` value is authored in Rust catalog code, not user-input). |
| T-18-01-03 | DoS | Tailwind safelist expansion | accept | Adds ~22 class literals to the @source inline arg; tailwind JIT compile-time cost is negligible (<5ms delta, verified by pnpm build time). No runtime effect. |
| T-18-01-04 | Spoofing | `icon` prop resolving to lucide icon | mitigate | Svelte-side icon resolution uses the `icons.ts` registry (not arbitrary `@lucide/svelte/icons/*` imports from props) — an unknown kebab name yields no icon render. The registry is the allowlist. Task 2 must route `props.icon` through the existing `IconRenderer` registry helper, not a dynamic import. |
</threat_model>
