From frontend/src/lib/components/form/TextInput.svelte lines 45-56 (the exact handleBlur function; copy structure into the 4 targets):
```svelte
function handleBlur() {
    if (bind) {
        clearDirty(bind, (op) => setData(surface, op.path, op.value));
        if (action?.type === 'blur') {
            sendAction(
                action.name ?? action.type,
                { value: getData(surface, bind!) },
                action.target
            );
        }
    }
}
```

Then on the DOM element:
```svelte
<Input ... onblur={handleBlur} />
```

Per-component wire-up (from PATTERNS.md lines 758-775 + RESEARCH.md §Q1):

| Component | Element for blur signal | Implementation |
|-----------|------------------------|----------------|
| SelectInput.svelte | popover close | hook into existing `handleOpenChange(open: boolean)` — when `open === false`, call `handleBlur()` |
| Checkbox.svelte | focusout on the Field wrapper (bits-ui checkbox does NOT expose native onblur reliably) | wrap in `<div onfocusout={handleBlur}>` |
| Switch.svelte | focusout on the Field wrapper | wrap in `<div onfocusout={handleBlur}>` |
| RadioGroup.svelte | focusout on the group | wrap in `<div onfocusout={handleBlur}>` |

Value payload shape — all four components send `{ value: getData(surface, bind!) }`. The backend handler reads `ctx.action.payload.get("value")`. Types:
- SelectInput: string (chosen option value, or `""` when cleared)
- Checkbox: boolean (`true` / `false`)
- Switch: boolean
- RadioGroup: string (selected option value, or `""`)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser DOM → WS `sendAction` payload | Blur handler captures the currently bound value from the frontend data store and sends it as `{ value: <primitive> }`. The value originates from user input but is echoed back to the server that seeded it. |
| WS payload → backend handler | Phase 18 validate-* handlers consume the `value` field; they must treat it as untrusted (classic input validation). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-02-01 | Tampering | Payload value field (string / boolean) | mitigate | Backend validate-* handlers (Plan 18-05) treat `ctx.action.payload.value` as untrusted; they never concatenate it into response strings without escaping and never pass it to downstream services. Rust's serde + strict typing give one layer; the handlers authored in 18-05 add the second (type-check `as_str()`/`as_bool()` and fall back safely). |
| T-18-02-02 | DoS | Focusout handler dispatch on every focus movement | mitigate | `clearDirty` is the only side effect on non-blur-action branches; the `sendAction` call fires at most once per focus-leave, which is naturally rate-limited by user interaction. No debouncing required — validation handlers are <5ms. Chrome MCP UAT in Plan 18-08 confirms responsiveness. |
| T-18-02-03 | Information disclosure | Payload value shape | accept | Payload is `{ value: <bound primitive> }`. No PII in Phase 18 (catalog form values are all demo-seeded strings / booleans: "bad-input", "Cannot edit", `true`, `false`). Even in a compromised scenario, no sensitive data exists to leak. |
| T-18-02-04 | Spoofing | `action.name` spoofable from Rust builder | accept | The builder is server-authored; a client cannot influence `action.name` because the Component tree is rendered server-side and delivered via the WS connection the server initiated. A compromised server is already game-over; client cannot forge actions into its own render. |
</threat_model>
