**Document structure (these are the required sections in order):**

**1. Header + Overview**
- Title: "OpenSDUI Protocol Specification"
- Version: 1.0.0
- One-paragraph summary: server-driven UI protocol, three primitives (components, data, messages), WebSocket transport
- Note: "This document is the authoritative protocol reference. See CONCEPT.md for design motivation."

**2. Three Primitives**
Brief explanation of components, data, messages as the three building blocks.

**3. Transport**
- WebSocket-only at `/ws` path
- Initial HTTP GET serves the SvelteKit app (static files), then WebSocket takes over
- No REST endpoints for protocol messages
- JSON text frames for all messages
- Connection lifecycle:
  1. Client opens WebSocket to `/ws`
  2. Server sends HelloMessage with protocol version
  3. Client sends initial action (e.g., navigate to current URL)
  4. Server sends RenderMessage(s) for active surfaces
  5. Ongoing: actions up, renders/patches/events/errors down
- Reconnection: exponential backoff starting at 1s, max 30s, jitter +/- 500ms. Server re-sends current render state on new connection. These are SHOULD (not MUST) parameters.
- Keepalive: Use WebSocket transport-level ping/pong frames. No application-level ping/pong messages.
- Address PROT-13 explicitly: "This protocol uses WebSocket exclusively. There are no REST endpoints for protocol messages."

**4. Messages**
For each of the 6 message types, document:
- Direction (server->client, client->server, or connection lifecycle)
- Purpose
- Required and optional fields (reference the schema)
- When to use it
- A fresh YAML example (NOT from CONCEPT.md)

Message types in order:
- **hello** (server->client, connection lifecycle): version handshake. Sent exactly once on connect.
- **render** (server->client): full surface state -- components + data. Fields: surface, root, nodes, data. Replaces previous content for that surface.
- **patch** (server->client): incremental data update. Fields: patch (array of PatchOperation). Does NOT modify component tree -- only data.
- **action** (client->server): user interaction or navigation. Fields: name, source?, payload?, id?, optimistic?. The optimistic field contains patches to apply immediately; server confirms or rolls back.
- **event** (server->client): notification without full re-render. Fields: name, surface?, hint?. Examples: "close" event to dismiss modal, "data-changed" hint to trigger refresh.
- **error** (server->client): protocol-level errors. Fields: errors (array of path + message). Distinguish from field validation: ErrorMessage is for protocol/transport errors. Field validation errors are data patches (e.g., patching `/ui/errors`).

**5. Components**
- Adjacency list: flat map of string IDs to Component objects. Root pointer identifies the tree root.
- Component structure: type (open string), props (open object), children (array of node IDs), bind (JSON Pointer), action (ComponentAction), visible (JSON Pointer to boolean)
- Component types are an open set -- the protocol does NOT enumerate them. The frontend library defines the vocabulary.
- `additionalProperties: false` on Component for strict envelope; `additionalProperties: true` on props for extension.

**6. Data Binding**
- JSON Pointer (RFC 6901) paths bind components to data
- Path syntax: `/key/subkey`, `/collection/item-id/field`
- Two-way: component reads from path, user edits write back to path
- Data is included in RenderMessage; updated via PatchMessage
- Example: component with `bind: "/user/email"` reads and writes `data.user.email`

**7. Keyed Collections**
- Collections use objects with stable string keys, NOT arrays
- Why: array indices are unstable -- insert/delete shifts indices, patches hit wrong items
- Pattern: `{id: value}` map with separate order array
- Example showing users collection with `/users/u-123/name` patch targeting the correct record
- Display order maintained in a separate array (e.g., `/userOrder: ["u-123", "u-456"]`)

**8. Optimistic Updates**
- Core protocol feature (not optional)
- ActionMessage includes `optimistic: { patch: [...] }` with PatchOperations
- Frontend applies patches immediately for responsive UI
- Server processes action and either confirms (sends authoritative patch) or rejects (sends error, frontend rolls back optimistic patches)
- Example: form submit with optimistic loading state

**9. Error Handling**
Two error mechanisms (clearly distinguish):
- **ErrorMessage** (type="error"): Protocol-level errors -- malformed action, unknown surface, server crash. Contains `errors` array with optional `path` and required `message`.
- **Validation errors as data**: Field-level validation errors are data patches. Backend patches error data (e.g., `/form/errors`) and components bind to it. This keeps errors in the reactive data model.

**10. Surfaces**
- Named render targets: main, sidebar, modal, toast (examples, not exhaustive)
- Each surface has independent component tree and data
- RenderMessage targets a specific surface
- Events can target a surface (e.g., close modal)

**11. Protocol Versioning**
- Version communicated via HelloMessage on connect
- Backend and frontend are deployed together (same bundle)
- Version field enables graceful handling of cached/stale frontends
- No in-band version negotiation -- mismatch means reconnect after update

**12. Schema Reference**
- Point to `spec/openapi.yaml` as the machine-readable specification
- List schema files: `schemas/common.yaml`, `schemas/component.yaml`, `schemas/data.yaml`, `schemas/message.yaml`
- Note: JSON Schema draft 2020-12 (per OpenAPI 3.1 alignment)

All examples in the manual MUST be fresh YAML (not copied from CONCEPT.md). Use realistic but different scenarios -- e.g., a contact list, a settings page, a notification flow.
