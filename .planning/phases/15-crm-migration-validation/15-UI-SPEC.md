# Phase 15 — UI Design Contract

> Visual and interaction contract for the CRM migration & validation phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Phase scope:** Apply the already-locked Phase 14 FormScreen composition recipe to four additional CRM form surfaces (company, user, interaction edit forms + inline tag-add / note-add), introduce a Rust-side `form_shell()` helper, wire per-field validation write-path via `/_errors/{bind}`, and sweep residual Flowbite vocabulary out of governance docs.
>
> **This is NOT a new-visual-language phase.** Phase 15 is structurally derivative of Phase 14. Every token, color, typography, spacing, and component anatomy decision is inherited verbatim from `.planning/phases/14-formscreen-enhancements/14-UI-SPEC.md`. Citations reference that canonical source rather than re-deriving.

## Spacing Scale

Inherited unchanged from Phase 14 UI-SPEC §Spacing Scale. Reference values retained here for executor convenience only; any conflict resolves to the Phase 14 spec.

| Token | Value | Usage in Phase 15 |
|-------|-------|-------------------|
| xs | 4px | Reserved; not applied in Phase 15 forms |
| sm | 8px | `gap-2` between action-row buttons (Save + Cancel); internal `Field.Field` label→control→description rhythm |
| md | 16px | `Field.Group` grid `gap-4` between sibling fields inside a `FieldSet` |
| lg | 24px | `space-y-6` between sibling `FieldSet` nodes inside a `Form` |

**Phase 15 authoritative spacing rules (all delegated to Phase 14 UI-SPEC):**

1. FieldSet responsive grid: `grid grid-cols-1 md:grid-cols-2 gap-4`.

4. 36px minimum interactive target height on all inputs, select triggers, textareas, radio items, switches, buttons (shadcn `h-9`).

Exceptions: none introduced by this phase.

## Per-Screen Composition Blueprint (NEW)

This section locks the FieldSet grouping for each migrated handler so planner tasks cannot drift and the UAT driver has a deterministic DOM-assertion target per screen. Every handler uses `form_shell()` (CONTEXT D-B1) to build the outer envelope; the table below defines the inner composition.

### 1. `company` edit form (`backend/crates/crm-demo/src/handlers/company.rs:190-215`)

| Structural Node | Contents | Legend / Label Copy |
|-----------------|----------|---------------------|
| `FieldSet` × 1 | `[name, website, address]` | "Company details" |
| Action row | `[Cancel, Save company]` | — |

- **Field count:** 3 → single FieldSet (CONTEXT D-I preference: ≤4 fields = 1 set).
- **Per-field `full_width`:** none. All three flow in the default 2-col desktop grid; `address` occupies one cell (if it outgrows its cell, planner may lift to `full_width=true` at execution; UAT must then re-baseline this screen).
- **FieldSeparator nodes:** none (single FieldSet).
- **Description copy:** `name` field gets a production description — see §Description Copy Contract.

### 2. `user` edit form (`backend/crates/crm-demo/src/handlers/user.rs:217-260`)

| Structural Node | Contents | Legend / Label Copy |
|-----------------|----------|---------------------|
| `FieldSet` × 1 | `[name, email, password]` | "Account" |
| `FieldSeparator` × 1 | — | — |
| `FieldSet` × 2 | `[role, preferred_contact_method]` | "Permissions" |
| Action row | `[Cancel, Save user]` | — |

- **Field count:** 5 → two FieldSets split on semantic boundary (CONTEXT D-I preference: 5+ fields = 2 sets; Phase 14 contact-edit 3-set precedent).
- **`preferred_contact_method` is the new RadioGroup** (CONTEXT D-E2): options `[("email","Email"),("sms","SMS"),("phone","Phone")]`, rendered vertically. Not persisted (`#[allow(dead_code)]` per CONTEXT D-E2).
- **Per-field `full_width`:** none.
- **FieldSeparator rendering:** one `field-separator` adjacency-list node between the two FieldSets — explicit node path per Phase 14 D-C2 preference.
- **Description copy:** `email` field gets a production description; three per-option descriptions on `preferred_contact_method` — see §Description Copy Contract.

### 3. `interaction` edit form (`backend/crates/crm-demo/src/handlers/interaction.rs:63-109`)

| Structural Node | Contents | Legend / Label Copy |
|-----------------|----------|---------------------|
| `FieldSet` × 1 | `[type (RadioGroup), subject, date, notes (Textarea full_width)]` | "Interaction" |
| Action row | `[Cancel, Save interaction]` | — |

- **Field count:** 4 → single FieldSet (CONTEXT D-I preference).
- **`type` migrates from Select to RadioGroup** (CONTEXT D-E1): options `[("call","Call"),("email","Email"),("meeting","Meeting")]`. Vertical stack; NO per-option descriptions (labels are self-explanatory).
- **`notes` is a Textarea with `full_width=true`** — spans the full 2-col row on desktop. Below 768px it already fills the single column; `full_width` affects desktop only.
- **FieldSeparator nodes:** none (single FieldSet).
- **Description copy:** `date` field gets a format description — see §Description Copy Contract.

### 4. `contact` edit form (`backend/crates/crm-demo/src/handlers/contact.rs:519-670`) — REFACTOR, NO VISUAL CHANGE

- **Visual contract:** IDENTICAL to Phase 14. Three `FieldSet`s with two `FieldSeparator`s, Textarea for notes, Switch for opt_in, action row.
- **What changes:** envelope construction compresses into `form_shell()` per CONTEXT D-B2. Fields also start persisting `country`, `notes`, `opt_in` (CONTEXT D-C3) — purely a DB-plumbing change.
- **Visual rebaseline:** NONE. Phase 14 UAT-01 snapshots remain the baseline; any diff in Phase 15 UAT is a regression, not a rebaseline.

### 5. Inline `tag-add` form (`backend/crates/crm-demo/src/handlers/contact.rs:716-760`)

| Structural Node | Contents |
|-----------------|----------|
| `Container class="flex gap-2 items-end"` × 1 | `[TextInput (label="Add tag"), Button("+ Add tag")]` |

- **No FieldSet.** Single-field forms don't need grouping; a FieldSet with one child wastes vertical space.
- **Inline layout:** horizontal flex with `items-end` so the button's baseline aligns with the input's bottom edge (the input carries label + description real estate above; button is just `h-9`).
- **Description copy:** omitted (label + placeholder convey enough).
- **Error display:** error path `/_errors/contactTagForm/tag` renders INSIDE the `Field.Field` below the input, NOT as a form-level banner. Consistent with §Validation Write-Path Visual Contract.
- **Action row:** the `+ Add tag` button IS the action row. No separate Cancel — inline forms auto-clear on success.

### 6. Inline `note-add` forms (`contact.rs:716-760` and `company.rs:318-330`)

- **Composition:** identical to tag-add but with a Textarea (`rows={3}`) instead of TextInput, and `+ Add note` button copy.
- **Layout:** `Container class="flex flex-col gap-2 items-end"` so the button sits flush-right below the Textarea.
- **No FieldSet.** Single-field.
- **Description copy:** omitted (placeholder conveys the ask).
- **Error display:** error path `/_errors/contactNoteForm/body` (or equivalent bind) — same contract as tag-add.

## Description Copy Contract (NEW)

Phase 14 proved the `Field.Description` render path under synthetic `__mrnSetData` UAT. Phase 15 ships production copy in handler builders.

### Placement Rules

- **Position:** below the input control, above any `Field.Error`. When an error is active, description is hidden (Phase 14 shadcn recipe behavior) and replaced by the error string in the same visual slot.
- **Color:** `text-muted-foreground` (inherited).
- **Size:** whatever Phase 14 shipped for production (12px or 14px — see Typography note; do not re-decide).
- **Line length:** prefer ≤12 words per line; rely on natural wrapping if longer.

### Tone Rules

- **Sentence case.** Ends with a full stop unless the copy is a format spec.
- **Action-oriented.** "Will appear on invoices" not "This field will appear on invoices if you enter a value."
- **No hedging.** Do not say "if you enter…" — if the description only applies when the field is non-empty, say "When provided, …"
- **No marketing voice.** Factual, brief, respectful.

### Production Copy Strings (locked for Phase 15 handlers)

| Handler | Field | Description String |
|---------|-------|-------------------|
| `company` | `name` | "Will appear on invoices and contact details." |
| `user` | `email` | "Used for password resets and notifications." |
| `interaction` | `date` | "Format: YYYY-MM-DD HH:MM (24-hour)." |
| `user.preferred_contact_method` option `email` | — | "Receive updates by email." |
| `user.preferred_contact_method` option `sms` | — | "Text messages to your phone." |
| `user.preferred_contact_method` option `phone` | — | "A human will call you." |

**Rationale for locking exact strings:** Phase 15 executor and UAT driver need matching text for DOM assertions. If a handler deviates, UAT fails noisily — which is the intended guardrail.

**Other migrated fields (website, address, role, subject, notes, type, password, inline tag/note inputs):** `description=None` for Phase 15. Handler authors MAY add descriptions later if user feedback requests them, but Phase 15 ships the above six and nothing more. This keeps the UAT deterministic and respects CONTEXT D-E3 ("at least one field per migrated form" — company gets 1, user gets 1 + 3 option descriptions, interaction gets 1).

## Validation Write-Path Visual Contract (NEW)

Phase 14 proved the render path (synthetic UAT). Phase 15 makes it real — save handlers emit per-field `SetData` patches to `/_errors/{bind}` instead of form-level `BadPayload` toasts (CONTEXT D-D1).

### Visual Triggers (all inherited from Phase 14, formalized here)

1. **Error appears INSIDE the `Field.Field`,** below `Field.Description` (description auto-hides while error is active).
2. **Text color:** `text-destructive` (OKLCH red — see §Color).
3. **Wrapper attribute:** `data-invalid` attribute added to the `Field.Field` wrapper (omitted when no error).
4. **Control attribute:** `aria-invalid="true"` added to the `<input>` / `<select>` / `<textarea>` / radio item / switch (omitted when no error).
5. **Border + ring on control:** automatic via shadcn's `aria-invalid:*` utility classes. Destructive OKLCH replaces the default input border + focus ring.

### Multi-Field Error Semantics

When a save handler returns multiple field errors in a single `PatchMessage`, the frontend renders them independently:

- Each invalid field's `Field.Error` shows its own string.
- No aggregate banner at the top (form-level banner is RESERVED for non-field errors per CONTEXT D-D4).
- Field errors render in document order (the order `SetData` ops appear in the patch does not matter — the data store is keyed by path).

### Clearing Semantics

- On next successful input change, the frontend writes the new value via `setData(surface, bind, value)`. This does NOT clear the error — the server is authoritative.
- On next handler submission (or re-validation event), the handler re-validates and emits an **empty-string `SetData`** to `/_errors/{bind}` for any field that is now valid. Empty string → Field.Error hidden.
- No optimistic client-side error clearing. No debouncing of error state.

### Form-Level Error Banner (inherited from Phase 14, unchanged)

- **Trigger:** `/_errors/{form_bind}` resolves to a non-empty array (not a string).
- **Use cases in Phase 15:** auth failure ("Your session expired. Sign in again."), DB constraint violation ("This email is already registered."), optimistic-concurrency failure if applicable.
- **Placement:** above the form's first FieldSet, full width. Does NOT replace per-field errors — both can coexist if the handler emits both.
- **Styling:** `bg-destructive/10 border border-destructive/50 text-destructive rounded-md p-4 mb-4` (Phase 14 UI-SPEC §Form).

### Copywriting Contract for Field Errors (NEW for production handlers)

Phase 14 defined the shape (sentence case, ends with full stop, actionable). Phase 15 adds examples that handler authors MUST prefer when writing `validation_error_patch()` calls:

| Situation | Preferred Copy | Anti-Pattern |
|-----------|----------------|--------------|
| Required field empty | "Name is required." | "Please enter a name." (please-language) |
| Email format invalid | "Enter a valid email address." | "Invalid." (not actionable) |
| Too short | "Password must be at least 8 characters." | "Too short." (not specific) |
| Duplicate value | "This email is already registered. Try signing in." | "Email exists." (not actionable) |
| Out-of-range date | "Date must be in the past." | "Invalid date." (not specific) |
| Enum mismatch (RadioGroup/Select) | "Choose one of the listed options." | "Invalid value." (meaningless to user) |

These strings are suggestions for planner + executor; they do NOT have UAT-driven lock-in unless a specific handler ships them (UAT checks shape, not exact copy, for dynamic errors).
