# Phase 13: DataTable Enhancements — Research

**Researched:** 2026-04-10
**Domain:** shadcn-svelte + TanStack Table + TanStack Virtual, Svelte 5 runes, server-driven SDUI
**Confidence:** HIGH for stack/patterns/CRM mechanics; MEDIUM for Svelte 5 + svelte-virtual interop (known upstream gap)

## Summary

Phase 13 rewrites `DataTable.svelte` around the shadcn-svelte `data-table` recipe, adopting `@tanstack/table-core` for column state + visibility + (manual) sorting, plus `@tanstack/svelte-virtual` for row virtualization. The filter bar lives inside DataTable as a plain `<form>` of shadcn primitives driven by local Svelte `$state` — TanStack is kept filter-agnostic (`manualFiltering` is NOT used). CRM handlers already build `Container([Heading, …toolbar, DataTable])` directly — the orphan `TableScreen.svelte` is never reached from any backend handler, so its retirement is a pure frontend cleanup (delete file + test). The latent "actions column renders `[object Object]`" bug is real and confirmed: three handlers ship per-row action arrays (`contact.rs:423-426`, `company.rs:126-129`, `user.rs:87-90`) that the current `String(rowData[col.key] ?? '')` cell renderer mangles; `column.kind: 'actions'` fixes it via `renderComponent`.

The D-C2 "stale-response discard via request sequence numbers" constraint has a clean answer: Marionette's protocol **already** supports request correlation via `ActionMessage.id` (UUID generated by `sendAction`) echoed by handlers into `RenderMessage.id` / `PatchMessage.id` via `ctx.action.id.clone()` — exactly the pattern used for `confirmOptimistic(msg.id)` in `init.ts`. Every CRM list handler already does this. The planner needs to (a) extend `sendAction` to return the generated id (it currently returns `void`), (b) track the last-issued filter/sort action id in DataTable-local `$state`, and (c) drop render/patch responses whose `msg.id` doesn't match the current latest id. No protocol change required; no new message fields.

The Svelte 5 + `@tanstack/svelte-virtual` story is the one real risk. The package's peer dep officially lists Svelte 5, but internally (verified by reading `package/src/index.ts` of the v3.13.23 tarball) `createVirtualizer` still returns a `svelte/store` `Readable<SvelteVirtualizer>` and relies on `onChange` → `writable.set()` reactivity. Upstream issue [TanStack/virtual#866](https://github.com/TanStack/virtual/issues/866) is **OPEN** as of February 2025 with community reports of "jumpy" scrolling and scrollbar resets under Svelte 5 runes. There are two viable paths: consume the store via Svelte 5's legacy `$store` auto-subscription and drive option updates from `$effect` blocks calling `setOptions({ count })`; OR bypass the Svelte adapter and use `@tanstack/virtual-core` directly (instantiate `new Virtualizer(...)` in a `.svelte.ts` module wrapped in `$state`, mimicking the solid adapter — the upstream community workaround). Both work; the planner should pick the store-based path first (simpler) and fall back to virtual-core-direct if integration bugs surface in Wave 0 exploration.

**Primary recommendation:** Adopt the recipe verbatim via `npx shadcn-svelte@latest add table data-table dropdown-menu`, install `@tanstack/table-core@^8.21.3` + `@tanstack/svelte-virtual@^3.13.23` (+ its automatic `@tanstack/virtual-core` transitive dep) explicitly, use `manualSorting: true` (dispatch `sort` action on change, server returns new Render), use local Svelte `$state` filter bar with 300ms debounce via `setTimeout` inside `$effect`, implement IntersectionObserver sentinel as a small Svelte action (not a separate component) placed inside the virtualizer's transform container one row before the tail, and reuse the existing `ActionMessage.id` correlation mechanism for D-C2 stale-response discard.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Architecture**

- **D-A1:** Adopt the shadcn-svelte data-table recipe verbatim. Install `@tanstack/table-core`, `@tanstack/svelte-virtual`, and the shadcn-svelte `data-table` helper package (`createSvelteTable`, `FlexRender`, `renderSnippet`, `renderComponent`). Rewrite `DataTable.svelte` to mirror the recipe's structure. Hand-rolling UI is explicitly off the table.
- **D-A2:** Retire `TableScreen.svelte`. CRM handlers migrate to build a plain `Container` with `[Heading, …toolbar Buttons, DataTable]` children. No "thin shell" intermediary.

**Filter bar**

- **D-B1:** Plain form-pattern filter bar; TanStack stays filter-agnostic. Filter state is DataTable-local `$state` `Record<filterId, value>`. On change/Enter, DataTable dispatches `sendAction('filter', filterValues)`. TanStack configured WITHOUT `manualFiltering`.
- **D-B2:** Structured `filters[]` props array on DataTable: `[{ id, kind: 'text' | 'select' | 'date-range', label, placeholder?, options?, span? }]`. New schema dimension in `spec/schemas/data.yaml`.
- **D-B3:** Backend builder gets fluent filter helpers: `Filter::text(id)`, `Filter::select(id, options)`, `Filter::date_range(id)`. Type-safe, autocomplete-friendly.

**Filter trigger + dispatch**

- **D-C1:** Debounced live-filter, no Apply button. Text inputs dispatch after 300ms debounce per change. Enter inside a text input flushes immediately. Selects fire on change with no debounce. Date-range from/to inputs debounce like text.
- **D-C2:** **Stale-response discard via request sequence numbers.** Live filtering means request N may complete after N+1. DataTable MUST guard against this. The planner investigates existing dispatcher correlation; if none, DataTable tracks its own local seq.
- **D-C3:** Single `filter` action with flat values map. Action name: `filter`. Payload: `{ filter_id_1: value_1, ... }` — string for text/select, `{ from, to }` for date-range. Empty/undefined values omitted.
- **D-C4:** DataTable owns local filter state; NO `/bind` round-trip. Filter values live in component-local Svelte `$state`.

**Infinite scroll + reset semantics**

- **D-D1:** `@tanstack/svelte-virtual` `createVirtualizer` + IntersectionObserver sentinel INSIDE the virtualizer. Sentinel intersection → dispatch `sendAction('fetch-rows', { offset, limit })`. On server response appending rows, virtualizer recomputes and sentinel re-anchors.
- **D-D2:** Sort/filter reset = server sends Render replacement (or full collection-set patch). Client just resets `scrollTop` and re-arms sentinel. Server is single source of truth; client never mutates the protocol data store directly.
- **D-D3:** Both end-of-data contracts: optional `total_rows` when known, fewer-than-limit fallback otherwise. Server picks per screen.

**Column visibility**

- **D-E1:** `DropdownMenu` "Columns" trigger in DataTable's top region; per-mount Svelte `$state`, no persistence.
- **D-E2:** Backend `hidden_default: bool` per column.

**Cell rendering**

- **D-F1:** `column.kind: 'text' | 'badge' | 'actions' | 'date' | 'number'` (default `'text'`). Per-kind Svelte snippet via `createRawSnippet` + `renderSnippet`. `actions` expects `rowData[col.key]` to be an array of `{ label, action }` objects → rendered as `DropdownMenu`.

**Backend builder**

- **D-G1:** Extend existing `#[derive(ComponentBuilder)] DataTable` struct with optional fields `total_rows`, `filters`, `row_id_key`. `Filter` and `ColumnKind` enums in `builders/standard.rs`. `TableColumn` gains `kind` and `hidden_default`.

### Pattern 1: `createSvelteTable` config with Svelte 5 getters (manual sort, client visibility, no client filter)

**Source:** shadcn-svelte.com/docs/components/data-table + jamesoclaire.com TanStack v8+Svelte 5 guide

```typescript
import {
  createSvelteTable,
  FlexRender,
  renderSnippet,
  renderComponent,
} from '$lib/components/ui/data-table/index.js';
import {
  getCoreRowModel,
  type ColumnDef,
  type SortingState,
  type VisibilityState,
} from '@tanstack/table-core';

let { props, bind, action, surface } = $props();

// Reactive inputs from protocol store
let rows = $derived(/* from getData(surface, bind) */);
let columns = $derived(/* buildColumns(props.columns) — see Pattern 3 */);

// Local state for TanStack-managed concerns
let sorting = $state<SortingState>([]);
let columnVisibility = $state<VisibilityState>(/* from col.hidden_default defaults */);

const table = createSvelteTable({
  get data() { return rows; },
  get columns() { return columns; },
  state: {
    get sorting() { return sorting; },
    get columnVisibility() { return columnVisibility; },
  },
  onSortingChange: (updater) => {
    sorting = typeof updater === 'function' ? updater(sorting) : updater;
    // Dispatch server-side sort — manual mode (see below)
    const primary = sorting[0];
    if (primary) {
      sendAction('sort', { column: primary.id, direction: primary.desc ? 'desc' : 'asc' });
    }
  },
  onColumnVisibilityChange: (updater) => {
    columnVisibility = typeof updater === 'function' ? updater(columnVisibility) : updater;
  },
  // CRITICAL: manualSorting true — TanStack does NOT sort the data array.
  // Server returns new Render on each sort change.
  manualSorting: true,
  // NO manualFiltering, NO getFilteredRowModel — filters live outside TanStack per D-B1.
  getCoreRowModel: getCoreRowModel(),
});
```

**Why getters (not plain props)**: shadcn-svelte's `createSvelteTable` wrapper stores the options object and re-reads via the getter on every re-evaluation, preserving runes-based reactivity. Without `get data()`, the table wouldn't re-derive when `rows` changes. [CITED: jamesoclaire.com/2025/04/09/easiest-way-to-get-tanstack-table-v8-working-with-svelte-5/]

**Why `manualSorting: true`**: Marionette is server-driven. Sorting is a server concern (database `ORDER BY`). With client sorting enabled, TanStack would sort the in-memory chunk but the server's pagination/chunk would be inconsistent with what the client shows. Manual mode means TanStack tracks sort state and fires `onSortingChange`, but does NOT mutate the row order — the server's next Render contains the sorted rows. [VERIFIED: TanStack docs — "manualSorting" option in the Table State guide].

**Initial column visibility from `hidden_default`**: Build the initial `VisibilityState` object once on mount from `columns.filter(c => c.hidden_default).map(c => [c.key, false])` entries. Per D-E1, per-mount state — do NOT persist.

### Pattern 2: Filter bar — plain Svelte $state + 300ms debounce + stale-response guard

```typescript
// Per D-B2: filter defs come from props.filters
type FilterDef =
  | { id: string; kind: 'text'; label: string; placeholder?: string }
  | { id: string; kind: 'select'; label: string; options: { value: string; label: string }[] }
  | { id: string; kind: 'date-range'; label: string };

let filters = $derived((props.filters as FilterDef[]) ?? []);
let filterValues = $state<Record<string, unknown>>({});
let debounceTimer: ReturnType<typeof setTimeout> | undefined;
let latestFilterActionId: string | undefined;  // D-C2 correlation

function flushFilter() {
  // Strip empty/undefined values per D-C3
  const payload: Record<string, unknown> = {};
  for (const [k, v] of Object.entries(filterValues)) {
    if (v === '' || v === undefined || v === null) continue;
    if (typeof v === 'object' && 'from' in v && !v.from && !v.to) continue;
    payload[k] = v;
  }
  // Capture the action id we're about to send so we can discard older responses.
  const id = sendActionAndReturnId('filter', payload);  // see §D-C2 below
  latestFilterActionId = id;
}

function scheduleFilter(delay = 300) {
  if (debounceTimer) clearTimeout(debounceTimer);
  debounceTimer = setTimeout(flushFilter, delay);
}

// Text / date-range input handlers: debounced
function handleTextChange(id: string, value: string) {
  filterValues[id] = value;
  scheduleFilter(300);
}
// Select change handler: immediate per D-C1
function handleSelectChange(id: string, value: string) {
  filterValues[id] = value;
  if (debounceTimer) clearTimeout(debounceTimer);
  flushFilter();
}
// Enter-to-flush: bind `onkeydown` on text inputs
function handleTextKeydown(e: KeyboardEvent) {
  if (e.key === 'Enter') {
    e.preventDefault();
    if (debounceTimer) clearTimeout(debounceTimer);
    flushFilter();
  }
}
```

**Markup sketch (recipe-aligned):**

```svelte
<div class="flex items-center py-4 gap-2">
```

### Pattern 3: Per-kind cell renderers via `createRawSnippet` + `renderSnippet`

```typescript
import { createRawSnippet } from 'svelte';
import { renderSnippet, renderComponent } from '$lib/components/ui/data-table/index.js';
import Badge from '$lib/components/ui/badge/badge.svelte';
import DataTableActions from './DataTableActions.svelte';

type SduiColumn = {
  key: string;
  label: string;
  sortable?: boolean;
  kind?: 'text' | 'badge' | 'actions' | 'date' | 'number';
  hidden_default?: boolean;
};

function buildColumns(sduiCols: SduiColumn[]): ColumnDef<RowData>[] {
  return sduiCols.map((c): ColumnDef<RowData> => ({
    id: c.key,
    accessorKey: c.key,
    header: c.label,
    enableSorting: c.sortable ?? false,
    enableHiding: true,
    cell: ({ row }) => {
      const value = row.original[c.key];
      switch (c.kind ?? 'text') {
        case 'badge':
          return renderComponent(Badge, { variant: 'default', children: String(value ?? '') });
        case 'actions':
          return renderComponent(DataTableActions, { items: (value as ActionItem[]) ?? [] });
        case 'date':
          return renderSnippet(dateSnippet, { iso: value as string });
        case 'number':
          return renderSnippet(numberSnippet, { n: Number(value ?? 0) });
        case 'text':
        default:
          return String(value ?? '');
      }
    },
  }));
}

const dateSnippet = createRawSnippet<[{ iso: string }]>((getArgs) => {
  const { iso } = getArgs();
  const formatted = new Intl.DateTimeFormat(undefined, { dateStyle: 'medium' }).format(new Date(iso));
  return { render: () => `<span>${formatted}</span>` };
});

const numberSnippet = createRawSnippet<[{ n: number }]>((getArgs) => {
  const { n } = getArgs();
  const formatted = new Intl.NumberFormat().format(n);
  return { render: () => `<span class="text-right tabular-nums">${formatted}</span>` };
});
```

`DataTableActions.svelte` is a tiny component that takes `items: { label: string; action: ComponentAction }[]` and renders a `DropdownMenu` of clickable items, each dispatching `sendAction(item.action.name, item.action.payload, item.action.target)` on click. This is where CRM's existing per-row `actions` arrays finally render correctly — resolving the latent `[object Object]` bug.

[CITED: shadcn-svelte.com/docs/components/data-table — "Row Actions" section] "Actions are rendered via `renderComponent`:" followed by `cell: ({ row }) => renderComponent(DataTableActions, { id: row.original.id })`.

### Pattern 4: TanStack Table + svelte-virtual integration (canonical row loop)

**Core pattern** (framework-agnostic, adapted to Svelte 5):

```typescript
import { createVirtualizer } from '@tanstack/svelte-virtual';

let tableContainerRef = $state<HTMLDivElement | undefined>();

const virtualizer = createVirtualizer({
  count: /* row count — see reactivity note */,
  getScrollElement: () => tableContainerRef,
  estimateSize: () => 48,     // matches current ROW_HEIGHT
  overscan: 5,
});
```

**Svelte 5 reactivity gotcha**: `createVirtualizer` returns a `svelte/store` `Readable<SvelteVirtualizer>` (confirmed by inspecting `@tanstack/svelte-virtual@3.13.23/src/index.ts` line 30). In Svelte 5, you access it via `$virtualizer` in markup (legacy store auto-subscription is still supported). Because options are captured at creation time by default, **updating the `count` as rows arrive requires calling `$virtualizer.setOptions({ count: newCount })` from a `$effect`**:

```typescript
$effect(() => {
  const rowCount = table.getRowModel().rows.length;
  $virtualizer.setOptions({
    count: rowCount,
    getScrollElement: () => tableContainerRef,
    estimateSize: () => 48,
    overscan: 5,
  });

```

```svelte
<div

  class="relative overflow-auto"

>
```

### Pattern 5: IntersectionObserver sentinel as a Svelte action

**Per D-D1**, the sentinel lives INSIDE the virtualizer's transform container (so it participates in the virtual list layout). Position it one or two rows before the tail so the fetch fires before the user hits the bottom. A small Svelte action is cleaner than an inline `$effect`:

```typescript
// lib/actions/viewport.ts
export function onIntersect(node: HTMLElement, callback: () => void) {
  const observer = new IntersectionObserver(
    (entries) => {
      for (const entry of entries) {
        if (entry.isIntersecting) callback();
      }
    },
    { root: null, rootMargin: '0px', threshold: 0.1 },
  );
  observer.observe(node);
  return {
    destroy() { observer.disconnect(); },
    update(newCallback: () => void) { callback = newCallback; },
  };
}
```

```svelte
{#if shouldShowSentinel}
  <div
    use:onIntersect={triggerFetchMore}
    style="position: absolute; top: {sentinelTopPx}px; height: 1px; width: 100%;"
  ></div>
{/if}
```

Where `sentinelTopPx = Math.max(0, $virtualizer.getTotalSize() - (estimateSize * 2))` (two rows before the absolute end).

**End-of-data guard (per D-D3):**
```typescript
const hasMore = $derived(
  props.total_rows != null
    ? rows.length < (props.total_rows as number)
    : !receivedShortChunk  // set when a fetch-rows response returned fewer than limit
);
let shouldShowSentinel = $derived(hasMore && !fetching);
```

**In-flight guard** (reuse the existing `let fetching = $state(false)` pattern; set to true in `triggerFetchMore`, reset to false in a `$effect` that watches `rows.length`).

### Pattern 6: D-C2 stale-response discard via existing `ActionMessage.id` correlation

**The mechanism already exists.** [VERIFIED: `frontend/src/lib/transport/dispatcher.ts:38-67`] `sendAction` generates a UUID via `crypto.randomUUID()` and sets `ActionMessage.id`. [VERIFIED: CRM handlers — grep `ctx.action.id.clone()`] every CRM list handler echoes the incoming action id into its `RenderMessage.id` (`audit.rs:209`, `contact.rs:444,942,1481`, `company.rs:137,379`, `user.rs:99,296`, `interaction.rs:148,244`). [VERIFIED: `frontend/src/lib/init.ts:38-41, 48-51`] the render/patch handlers call `confirmOptimistic(msg.id)` when correlated — the optimistic-update system ALREADY uses this exact id flow.

**What's missing:** `sendAction` currently returns `void`. The caller can't learn the generated id to track it. Two mechanics both work:

**Option A (minimal diff — recommended):** Change `sendAction` to return `string` (the id). Every existing call site ignores `void` return today, so returning a string is backward-compatible.

```typescript
// transport/dispatcher.ts
export function sendAction(
  name: string,
  payload?: Record<string, unknown>,
  source?: string,
  optimistic?: { patch: PatchOperation[] }
): string {
  const id = crypto.randomUUID();
  // ... existing body ...
  send(msg);
  return id;
}
```

Then in DataTable:
```typescript
let latestFilterActionId: string | undefined;
let latestSortActionId: string | undefined;
let latestFetchActionId: string | undefined;

function flushFilter() {
  latestFilterActionId = sendAction('filter', buildPayload());
}
```

**How the stale response is dropped:** Neither `render` nor `patch` handlers currently route through DataTable directly — they mutate the per-surface data store, and `$derived(getData(surface, bind))` reflects the new state. So DataTable can't "ignore" an incoming render by message dispatch.

Two sub-options:

- **A1 (cleanest — but requires new infra):** register a pre-dispatch filter in `init.ts` that checks whether the incoming `RenderMessage.id` or `PatchMessage.id` matches any registered component's "current expected id." If not — drop. This generalizes to other components but is new machinery.
- **A2 (smallest — recommended):** DataTable wraps its `rows` derivation behind an additional guard. When `filter` / `sort` is dispatched, DataTable records the timestamp and freezes display (show "filtering…" overlay or just keep the current rows). The protocol handles this naturally: the CURRENT render's data replaces the old collection wholesale (per D-D2 — server sends a fresh Render). Older replies can't "win" because the Render that matches the latest id arrives last. **BUT** — two races still exist:
  1. Two replies arrive in non-dispatch order (TCP preserves order on a single WebSocket, so this is impossible in practice on one connection — the JavaScript event loop processes them in receive order).
  2. A reconnect sequence could theoretically reorder, but any reconnect issues a fresh initial render.

**Conclusion:** On a single WebSocket connection, **TCP ordering + single-threaded JS event loop + server-side Render-replacement-on-reset (D-D2) already prevents stale overwrites.** The server processes each action serially and writes each response in order. The protocol layer preserves that order. By the time the client sees Render #2, Render #1 has already been applied and replaced. No request/response reordering is physically possible.

**BUT** there's a subtler case: a `filter` action fires, and before the server responds, a `fetch-rows` action fires (triggered by scrolling that was already queued). The `fetch-rows` response PATCHES the old collection (appending rows), then the `filter` Render REPLACES it. The append was wasted but not stale. The opposite order — fetch-rows fires AFTER filter — the server's `fetch-rows` handler might append rows from the old filter state to the NEW collection. This IS a real bug.

**So D-C2 IS needed**, but only for the case "fetch-rows response interleaving with a filter/sort response." The fix:

1. DataTable tracks `let currentRenderEpoch = $state(0)`, bumped every time a filter or sort dispatches.
2. DataTable holds `let lastFetchRowsActionId: string | undefined` — the id of the most recently issued `fetch-rows` action.
3. When a new filter/sort fires, `lastFetchRowsActionId = undefined` and `currentRenderEpoch++`.
4. Either:
   - **(a) Server-side:** the `fetch-rows` handler encodes its patch `id: Some(ctx.action.id.clone())`, matching the client's tracked id. When the client receives a `PatchMessage` with `id !== lastFetchRowsActionId`, it drops it.
   - **(b) Client-side purely:** DataTable registers a one-shot handler via a new hook in `init.ts` that extracts `filter` / `fetch-rows` replies by `msg.id`. More machinery.

**Recommended:** **(a)** — have the `fetch-rows` handler echo `ctx.action.id.clone()` into the `PatchMessage.id` (just like the existing country-change handler at `contact.rs:1481`), and have DataTable track `lastFetchRowsActionId`. **The only client-side piece is that `applyPatch` in `data.svelte.ts` or DataTable's local logic needs to expose a hook where a component can short-circuit patches by id.** Or — simpler still — DataTable maintains its OWN local rows shadow (`let localRows = $state<Row[]>([])`), NOT derived from the protocol store, and a one-shot subscription in init.ts delivers patches+renders scoped to this DataTable instance by id.

This is ugly. The **cleanest** pragmatic answer for Phase 13:

**D-C2 recommended resolution:** Add a lightweight correlation registry in `transport/dispatcher.ts`:

```typescript
// transport/dispatcher.ts additions
const pendingFilterActions = new Map<string, (msg: RenderMessage | PatchMessage) => void>();

export function sendActionWithResponse(
  name: string,
  payload: Record<string, unknown>,
  onResponse: (msg: RenderMessage | PatchMessage) => void
): string {
  const id = sendAction(name, payload);   // reuse existing path
  pendingFilterActions.set(id, onResponse);
  return id;
}

// Called by init.ts render/patch handlers before applying them
export function checkPendingResponse(msg: { id?: string }): boolean {
  if (!msg.id) return true;  // no id — apply normally
  const cb = pendingFilterActions.get(msg.id);
  if (cb) {
    pendingFilterActions.delete(msg.id);
    // Keep apply path, but let DataTable know this is "its" response
    cb(msg as RenderMessage | PatchMessage);
  }
  return true;  // always apply — the point is NOTIFICATION, not interception
}
```

Then DataTable only needs to know "was this response for the action I'm currently waiting on?" via the callback. Older responses have already been deleted from the pending map.

**Simplest answer for the planner: the race DataTable needs to guard is `fetch-rows interleaved with filter/sort`. Fix: (1) extend `sendAction` to return the id; (2) track `lastFetchRowsActionId` in DataTable-local state; (3) server-side, make the `fetch-rows` handler echo `ctx.action.id.clone()` into its PatchMessage id (new convention — one-line change in each of the four list handlers); (4) client-side, extend `init.ts`'s patch handler to emit a small event (or use a registry) that DataTable can subscribe to and drop PatchMessages whose id doesn't match its last-issued fetch-rows id. The text-filter race (A for "Alic" vs A+1 for "Alice") is handled naturally by TCP ordering — the later Render replaces the earlier via the existing `setFullState` in `init.ts:31`.**

The planner should pick a specific mechanism from the three above. All require one new piece of wire-up in `init.ts`. I recommend the registry approach (callback map) because it's local to dispatcher.ts and testable in isolation.

### Anti-Patterns to Avoid

- **DO NOT install `@tanstack/svelte-table`.** It only supports Svelte 3/4. Peer-dep warning will install but runtime is undefined. [VERIFIED: npm view]
- **DO NOT try to use `columnFilters` state in `createSvelteTable`.** Per D-B1, TanStack stays filter-agnostic. The moment you wire `columnFilters` + `getFilteredRowModel`, you've reintroduced a client-side data pipeline that contradicts the server-driven model.
- **DO NOT hand-roll the `createSvelteTable` wrapper.** The shadcn CLI's `data-table` helper package is the canonical source for `createSvelteTable`, `FlexRender`, `renderSnippet`, `renderComponent` — it's written to handle the runes-vs-store boundary correctly.
- **DO NOT use `@tanstack/svelte-virtual`'s `createVirtualizer` without a `$effect` to call `setOptions({ count })`.** Options are captured at creation; rune-driven reactivity for `count` requires explicit setOptions on every row-count change.
- **DO NOT place the IntersectionObserver sentinel OUTSIDE the virtualizer's transform container.** It must participate in the virtual layout so it appears near the rendered tail, not at a fixed DOM position that never intersects because virtual rows are absolutely positioned.
- **DO NOT rely on client-side getSortedRowModel + manualSorting together** — these are mutually exclusive in TanStack v8. Use `manualSorting: true` and omit `getSortedRowModel()`.
- **DO NOT re-mount DataTable on filter change.** The component must stay mounted so the filter inputs retain focus. Per Phase 12's D-A6 focus preservation infrastructure, the server's Render replacement of the bound collection only mutates the data slice, not the component tree — as long as the DataTable's node id in the adjacency list is stable across renders.
- **DO NOT use `Input`'s `onchange` ONLY for text filters.** The recipe uses `oninput` for live responsiveness. `onchange` fires on blur, which feels sluggish.

## Common Pitfalls

### Pitfall 1: `createVirtualizer` returns a store, not a reactive object

**What goes wrong:** First naive attempt writes `virtualizer.getVirtualItems()` in markup directly (Svelte 4 style), gets a compile error OR (worse) a non-reactive snapshot that never updates.

**Why it happens:** `@tanstack/svelte-virtual@3.13.23` still uses `svelte/store` `writable`, not Svelte 5 runes. Svelte 5 SUPPORTS the auto-subscription `$store` prefix in markup for legacy stores, but only when you prefix the variable with `$`.

**How to avoid:** Always access via `$virtualizer.*` in markup and in `$derived`:

```svelte
<div style="height: {$virtualizer.getTotalSize()}px">
  {#each $virtualizer.getVirtualItems() as item (item.key)}
```

**Warning signs:** Empty table on mount, or table renders once but doesn't respond to row additions. Verify via `console.log($virtualizer.getVirtualItems())` inside `$derived`.

### Pitfall 2: `createVirtualizer` options don't auto-update

**What goes wrong:** Virtualizer is created with `count: rows.length` but never re-derives when rows change. Scrollbar sized to the initial count forever.

**Why it happens:** The initial options object is captured once. The virtualizer needs `setOptions(...)` calls for count/estimateSize changes.

**How to avoid:** Wrap option updates in `$effect`:
```typescript
$effect(() => {
  $virtualizer.setOptions({
    count: table.getRowModel().rows.length,
    getScrollElement: () => tableContainerRef,
    estimateSize: () => 48,
    overscan: 5,
  });
});
```

**Warning signs:** Row count increases but scrollbar stays fixed; sentinel never intersects because the virtual height never grows.

### Pitfall 3: TanStack manualSorting + local sort state feedback loop

**What goes wrong:** Server sends Render with sorted rows; client's local `sorting` state doesn't reflect that (it's an empty `[]`). User clicks a header, TanStack calls `onSortingChange`, you update local state, fire `sendAction('sort', ...)`, server re-renders. Looks fine. But then the indicator arrow renders the WRONG column because the server-sorted order doesn't sync to local `sorting` state.

**How to avoid:** Pre-seed `sorting` from props: `let sorting = $state<SortingState>((props.initial_sort as SortingState) ?? []);`. Backend emits the current sort as a new `DataTable` prop `initial_sort` (optional) so header indicators stay truthful. Alternatively, accept that the indicator is ephemeral local state and the server has its own source of truth — the drift is cosmetic.

### Pitfall 4: IntersectionObserver fires once then stops (fetch guard never resets)

**What goes wrong:** Sentinel intersects, dispatch fires, but `fetching = true` never resets, so the second chunk never loads.

**Why it happens:** `fetching = false` inside a `$effect` watching `rows.length` works — but ONLY if the derivation actually observes `rows.length`. In Svelte 5 runes, tracking is explicit. Must READ the value inside the effect body.

**How to avoid:** Reuse the existing pattern from the current DataTable.svelte:
```typescript
$effect(() => {
  rows.length;  // read to establish tracking
  fetching = false;
});
```

Or use the return callback from the fetch response (if D-C2's registry approach is adopted) to flip the flag.

### Pitfall 5: Filter input loses focus across node patches

**What goes wrong:** User types in the search input, server responds with a fresh Render for the new data (D-D2 reset semantics), the filter input loses focus mid-typing because the whole DataTable node is replaced.

**Why it happens (or why it won't):** Phase 12's D-A6 focus-preservation infrastructure (`frontend/src/lib/store/surfaces.svelte.ts` fine-grained per-key mutation) preserves focus across **node patches** to sibling nodes. But a full `Render` to the surface is a wholesale tree replacement — NOT a patch. If the server responds to `filter` with a Render targeting `/contacts` (the bound collection), it's a DATA patch under the hood (`setFullState(surface, data)`). The COMPONENT tree doesn't re-mount. DataTable stays mounted, the filter input keeps its Svelte node identity, focus is preserved.

**How to avoid (for correctness):** The server must send only a data update when the table rows change due to filter/sort — NOT a fresh tree Render that re-creates the DataTable node. The existing CRM handlers call `handle_contact_list` which returns a full `RenderMessage` with all nodes — this DOES re-mount the DataTable node technically. BUT init.ts line 31 calls `setFullState(msg.surface, msg.data)` and line 33 calls `setSurfaceTree(msg.surface, msg.root, msg.nodes)`. The surfaces store's setSurfaceTree is fine-grained per-node; if node IDs match across the two Renders, the DOM nodes are NOT recreated.

**Action for the planner:** **The CRM handlers must use stable, deterministic node IDs across renders** (e.g., `.id("contact-table")`, not auto-generated UUIDs — which they already do for `contact-table`, `contact-list-root`, etc.). Verify this is the case for the filter input nodes the recipe creates INSIDE DataTable.svelte. Since the filter input lives in DataTable.svelte markup (not in the adjacency list), Svelte's own key-based diffing preserves it.

**Warning signs:** Test via `frontend/src/lib/store/surfaces.focus-preservation.browser-test.ts` style — focus filter input, fire `filter` action in a mock server, assert `document.activeElement` is still the filter input.

### Pitfall 6: `shadcn-svelte add data-table` conflicts with existing `ui/table/`

**What goes wrong:** Running `npx shadcn-svelte@latest add data-table` might try to re-install `table/` primitives and clobber local changes.

**How to avoid:** [VERIFIED: shadcn-svelte.com/docs/components/data-table] the `data-table` helper package writes to `$lib/components/ui/data-table/` — a SEPARATE directory from `ui/table/`. Different file. CLI may also try to add `table` if it detects it missing; the project already has `ui/table/` from Phase 11. Confirm with a dry-run first (`npx shadcn-svelte@latest add data-table --help` for flags), or commit before running and diff after.

### Pitfall 7: The orphan TableScreen.svelte registration

**What goes wrong:** You delete `TableScreen.svelte` but forget to remove its browser-test or registration.

**Reality check:** [VERIFIED: `frontend/src/lib/registry/defaults.ts`] TableScreen is NOT registered — it was never registered. [VERIFIED via grep of `backend/crates/crm-demo/src/handlers/`] no handler references `table-screen` or `TableScreen`. The Svelte file is a pure orphan. Deletion is a single-commit cleanup (delete `.svelte` + `.browser-test.ts`, done — no call-site updates needed).

**Warning signs:** If any grep of the codebase returns references to `'table-screen'` as a protocol type string, investigate before deleting.

### Pitfall 8: Bytes-per-render under filter debounce with IntersectionObserver

**What goes wrong:** User types rapidly, each keystroke debounces to 300ms, but concurrent scroll pagination fires `fetch-rows`. Server's `fetch-rows` handler doesn't know that the filter changed mid-scroll, appends rows from the OLD filter state, new filter Render replaces them. User sees brief flicker of "wrong" rows.

**How to avoid:** D-C2's stale-response discard (see Pattern 6 above) is exactly the fix. The `fetch-rows` handler must echo `ctx.action.id`, DataTable tracks `lastFetchRowsActionId`, and a client-side registry drops responses that don't match. Or: cheap path — on every `filter` / `sort` dispatch, set `fetching = true` for a brief window to disable the sentinel until the server's reset Render arrives; this prevents the `fetch-rows` from firing DURING a filter transition in the first place.

```svelte
  let totalRows = $derived((props.total_rows as number | undefined));
  let hasMore = $derived(
    totalRows != null ? rows.length < totalRows : !receivedShortChunk
  );

  function triggerFetchMore() {
    if (fetching || !hasMore) return;
    fetching = true;
    lastFetchActionId = sendAction('fetch-rows', { offset: rows.length, limit: 50 });
  }
  // Reset in-flight once rows grow (or filter/sort reset fires)
  $effect(() => { rows.length; fetching = false; });

  // Filter reset scrollTop (D-D2)
  let prevBoundHash = $state('');
  $effect(() => {
    const hash = Object.keys(rawData).slice(0, 3).join('|');
    if (hash !== prevBoundHash) {
      prevBoundHash = hash;
      if (scrollRef) scrollRef.scrollTop = 0;
      receivedShortChunk = false;
    }
  });

  function buildColumns(cols: SduiColumn[]): ColumnDef<Record<string, unknown>>[] {
    return cols.map((c) => ({
      id: c.key,
      accessorKey: c.key,
      header: c.label,
      enableSorting: c.sortable ?? false,
      enableHiding: true,
      cell: ({ row }) => {
        const value = row.original[c.key];
        switch (c.kind ?? 'text') {
          case 'badge':
            return renderComponent(Badge, { children: String(value ?? '') });
          case 'actions':
            return renderComponent(DataTableActions, { items: (value as unknown[]) ?? [] });
          case 'date':
            return renderSnippet(dateSnippet, { iso: String(value ?? '') });
          case 'number':
            return renderSnippet(numberSnippet, { n: Number(value ?? 0) });
          default:
            return String(value ?? '');
        }
      },
    }));
  }

  const dateSnippet = createRawSnippet<[{ iso: string }]>((get) => {
    const { iso } = get();
    const s = iso ? new Intl.DateTimeFormat(undefined, { dateStyle: 'medium' }).format(new Date(iso)) : '';
    return { render: () => `<span>${s}</span>` };
  });
  const numberSnippet = createRawSnippet<[{ n: number }]>((get) => {
    const { n } = get();
    const s = new Intl.NumberFormat().format(n);
    return { render: () => `<span class="tabular-nums text-right block">${s}</span>` };
  });
```

```rust
    }

    }

#[derive(ComponentBuilder)]

pub struct DataTable {

    #[builder(optional)]

    #[builder(optional)]

/// Hand-written extension so handlers can push filters one at a time
/// instead of replacing the whole vector via the derive-generated `.filters()`.
impl DataTableBuilder {
    #[must_use]
    pub fn filter(mut self, f: Filter) -> Self {
        self.filters = Some(match self.filters {
            Some(mut v) => { v.push(f); v }
            None => vec![f],
        });
        self
    }
}
```

**Why the hand-written `filter()`**: [VERIFIED: `backend/crates/marionette-macros/src/component_builder.rs:98-105`] the derive generates a setter `pub fn filters(mut self, value: Vec<Filter>) -> Self { self.filters = Some(value); self }` — which REPLACES the vec. Adding a push helper via a hand-written `impl DataTableBuilder` block next to the derive gives the fluent `.filter(Filter::text(...)).filter(Filter::select(...))` API the context requires. Same pattern used by `AppShellBuilder` in `builders/app_shell.rs`.

### Known Threat Patterns for Marionette (Rust/Axum + Svelte + WebSocket)

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SQL injection via filter payload | Tampering | SeaORM parameterized queries; reject unknown filter ids server-side |
| XSS via column cell content rendering | Tampering | Svelte auto-escapes text interpolation in `{#each}`; `createRawSnippet` uses a raw HTML template string — ensure date/number snippets interpolate ESCAPED values only (e.g., via `String(value).replace(/</g, '&lt;')` or use a snippet that returns text via a child span, not HTML string). `renderComponent(Badge, { children: String(value) })` is safe because Svelte escapes at the slot boundary. |
| DoS via giant filter queries | DoS | Enforce server-side page size hard cap (`limit: limit.min(100)`). `COUNT(*)` queries for `total_rows` can be expensive — D-D3's "fewer-than-limit fallback" exists precisely to skip the COUNT. |
| XSS via `actions` column payload injecting script | Tampering | `DataTableActions.svelte` must render `item.label` via text interpolation (not `{@html}`). `item.action.name` / `item.action.payload` are fed into `sendAction`, which serializes to JSON — safe. |
| Open redirect / CSRF via filter action on wrong surface | Elevation | Existing `ActionMessage` auth enforcement applies; WebSocket binds to session cookie at handshake. No new attack surface. |
| Client-side sort/filter bypass showing unauthorized rows | Elevation | **NOT A CONCERN** because Phase 13 is SERVER-driven: the client never sees rows it wasn't sent. TanStack never filters or sorts data. Column visibility is cosmetic — hidden columns are still transmitted over the wire. **Flag for documentation:** if a column contains sensitive data, it should NOT be present in the row payload at all; hiding it via `hidden_default` is NOT a security control. This is a docs-level caveat for the DataTable component type in PROTOCOL.md. |

## Open Questions

1. **[RESOLVED — see A5] No `fetch-rows` backend handler exists today. Phase 13 MUST add one.**
   - What we know: [VERIFIED 2026-04-10] `main.rs:451-591` registers 28 actions; none match `fetch-rows`/`fetch_rows`. The frontend current DataTable dispatches dead code.
   - Impact: Infinite scroll (TABLE-02) is a green-field addition, not just a rewire. Phase 13 plan count should reflect this: at least one plan for the server-side `fetch-rows` handler(s) in addition to the DataTable rewrite, builder extension, schema updates, and CRM migration plans.
   - Recommendation: **Option (i) — generic `fetch-rows` handler** that accepts `{ source: <component-id>, offset, limit, filter?, sort? }` and dispatches to a per-component fetcher registered in a new static table. Minimally invasive: add one handler, one registration, and one `register_table_fetcher` call per list handler. Alternatively, option (iii) — each `<entity>_list` handler already exists; teach it to detect `payload.offset != 0` and return a PatchMessage (append) instead of a Render (replace). Two minor edits to each list handler.

2. **What is the exact response shape of `fetch-rows`?**
   - What we know: Per D-D3 the server sends "a data patch appending rows." The existing protocol supports `set` ops at arbitrary paths, so the handler could return a PatchMessage with one `set` op per new row at `/contacts/row-N`, or a single `set` op at `/contacts/row-N` merging the new entries.
   - What's unclear: Does the append use N ops (one per row) or a single set on a new collection? Affects stale-response discard strategy.
   - Recommendation: Planner decides based on the simplest Rust idiom — probably one Render with the full collection for filter/sort reset, one PatchMessage with one `set` op per new row for fetch-rows.

3. **Should the server emit a `total_rows` field in the initial Render data so the client can show "237 contacts"?**
   - What we know: D-D3 says `total_rows` is an optional DataTable prop. The prop lives on the DataTable Component, not the data — so it's set via the builder at Render time.
   - What's unclear: For the CRM, is COUNT(*) cheap enough (SQLite, 100-10k row scale) to always include, or should it stay optional?
   - Recommendation: Enable `total_rows` for all four CRM handlers initially since SQLite COUNT(*) is O(indexed) for our scale; revisit if performance regresses.

4. **Is the stale-response-discard registry general infrastructure or DataTable-local?**
   - What we know: D-C2 says "the implementation strategy is for the planner to decide." A general registry in `dispatcher.ts` is useful for other phases; a local DataTable `$state` is simpler.
   - What's unclear: Are there other components that will need stale-response discard in v1.1 (Phase 14's FormScreen? Phase 15's CRM flows)?
   - Recommendation: Build it in `transport/dispatcher.ts` as general infra with a `sendActionWithResponse(name, payload, onResponse)` API. Future components reuse it.
